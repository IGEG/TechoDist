# ADR 0009. Search Service: Elasticsearch как индекс каталога

- **Статус:** Accepted
- **Дата:** 2026-10-04

## Контекст

Витрине нужен полнотекстовый поиск: запрос «установка» должен находить все модели,
«TD60» — конкретную, плюс фильтры по категории и диапазону цен, сортировка и пагинация.
PostgreSQL-запросы `ILIKE` не дают ни морфологии русского языка, ни ранжирования по
релевантности, а поиск по описаниям быстро упирается в производительность.

В стеке уже есть Elasticsearch (docker-compose инфраструктуры, Kibana для отладки),
и каталог уже публикует изменения товаров через transactional outbox (ADR 0003).
Нужно решить, где живёт поиск, откуда берутся данные и как индекс не расходится с каталогом.

## Решение

**Отдельный сервис `Search` с индексом Elasticsearch как денормализованной read-моделью
каталога. Источник истины — Catalog; своей БД у Search нет.**

- **Схема сервиса.** Три проекта Clean Architecture: `Techodist.Search.Application`
  (правила выдачи), `Techodist.Search.Infrastructure` (клиент Elasticsearch, чтение
  Catalog API, health-check), `Techodist.Search.Api` (контроллер, потребитель событий, DI).
  Хранилища нет, поэтому нет EF Core, миграций, outbox и JWT админ-эндпоинтов.
- **Обычный путь обновления — событие.** Catalog в одной транзакции с сохранением товара
  кладёт `ProductChangedIntegrationEvent` в outbox (снимок карточки: имя, slug, цена,
  категория, признак публикации). Search слушает очередь (`ProductChangedConsumer` →
  `ProductChangedIndexer`) и делает upsert/delete. Событие несёт готовый снимок, поэтому
  в момент индексации Search не ходит в Catalog (как Order → Notification, ADR 0002).
- **Индекс хранит только опубликованные товары.** Черновик, архив и удаление удаляют
  документ, а не помечают его: витрина физически не может показать снятый товар, а запрос
  не тащит лишний скоринг. Фильтр `isPublished` в запросе остаётся страховкой от ручной
  правки индекса и делает запрос самодостаточным.
- **Резервный путь — реконсиляция.** Событие может потеряться (Search был выключен, брокер
  перезапускался, индекс подняли с нуля), поэтому при старте и далее по расписанию
  (`Search:Reindex:IntervalMinutes`, по умолчанию 30 мин) фоновая служба читает публичный
  список опубликованных товаров Catalog API и доводит индекс до каталога. Сверка
  идемпотентна и ничего лишнего не удаляет: полная пересборка — операция сопровождения
  (удалить индекс и дать сервису наполнить его заново).
- **Маппинг индекса задан явно и создаётся сервисом.** Текст (название, описание, имя
  категории, slug, марка растворителя) индексируется анализатором `russian` — работают
  словоформы; фильтры и сортировка идут по `keyword`/числовым полям, которые анализировать
  нельзя. `name.keyword` служит tie-break релевантной выдачи, иначе страницы при равном
  скоре «перемешиваются». Индекс создаётся через `EnsureIndexAsync` перед первым наполнением:
  upsert в несуществующий индекс создал бы его с динамическим маппингом, и полнотекстовый
  поиск молча перестал бы находить словоформы.
- **Настройки клиента Elasticsearch.** `DefaultFieldNameInferrer(camelCase)` — имена полей
  документа совпадают с маппингом и с именами в запросах (`categoryId`, `isPublished`);
  иначе документы легли бы в другие поля, а поиск ничего бы не находил.
- **Правила выдачи живут в Application.** `ProductSearchFilter` нормализует страницу и размер
  (предел 50 — защита от выкачивания индекса), разбор ключей сортировки (`price_asc`,
  `price_desc`, `name_asc`, `name_desc` — те же, что в каталоге), отсечение заведомо пустого
  диапазона цен (`min > max` возвращает пустую выдачу без запроса к кластеру). Infrastructure
  остаётся «тонким» транспортом и не покрывается юнит-тестами.
- **API публичный.** Витрина не аутентифицируется (ADR 0004), админских операций у поиска
  нет: JWT в сервис не подключается, шлюз публикует маршрут `/search/**` без
  `AuthorizationPolicy`. Эндпоинт — `GET /api/search/products` (в контуре — `/search/api/search/products`).
- **Идемпотентность вместо журнала дедупликации.** `_id` документа — идентификатор товара,
  поэтому повторная доставка сообщения обновляет документ, а не создаёт дубль. Отдельное
  хранилище обработанных сообщений (как в Notification) избыточно.

## Последствия

- (+) Морфология и релевантность «из коробки», поиск не конкурирует с транзакционной БД
  каталога за ресурсы.
- (+) Индекс полностью восстановим: событие + реконсиляция дают одно и то же состояние,
  а сервис может быть поднят с нуля без миграций и бэкапов.
- (+) Read-модель денормализована (имя категории, картинка, цена): витрина рисует плитку
  товара без обращения к Catalog, один сетевой вызов на страницу выдачи.
- (−) Данные в выдаче на мгновение отстают от каталога (событие асинхронно) — для витрины
  магазина это приемлемо; заявка всё равно проверяется на стороне Order.
- (−) Появляется зависимость от Elasticsearch: недоступный кластер — это Unhealthy у
  health-check (ADR 0007), а не отказ всего сайта (каталог живёт на PostgreSQL).
- (−) Ручная правка индекса в Kibana может разойтись с маппингом — поэтому запросы держат
  фильтр `isPublished`, а полная пересборка описана как операция сопровождения.
